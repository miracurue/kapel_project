# Парсинг клинических рекомендаций в Colab

Откройте **`colab_clinrecs_docling_pipeline.ipynb`** в Google Colab через
«Файл → Загрузить блокнот». Весь рабочий Python-код встроен в него.
Загружать `.py`, клонировать проект или устанавливать что-либо на свой компьютер
для запуска в Colab не нужно.

1. Включите T4 GPU: «Среда выполнения → Сменить тип среды выполнения».
2. Выполните ячейку установки зависимостей.
3. В настройках оставьте `USE_DRIVE=True`, `CHUNK_PAGES=10`. Для первого теста
   поставьте `END_PAGE=10`; для полного документа — `END_PAGE=None`.
4. Подключите Google Drive и загрузите оба исходных PDF в ячейке загрузки.
5. Выполните проверку входных файлов, парсинг и скачивание ZIP.
6. Посмотрите `REPORT.md` и `quality_report.json`, откройте `document.md` вместе
   с папкой `images/`. Сверьте проблемные места с PDF.

По умолчанию файлы лежат в Google Drive:
`MyDrive/clinical_compass_clinrecs/input/` и `.../parsed/`.
При повторном запуске выберите `INPUT_MODE="drive"`: PDF уже сохранены.
Не запускайте две копии ноутбука с одной папкой результатов одновременно.

## Что изменено относительно исходных ноутбуков

| Было | Подготовленный вариант |
|---|---|
| Статьи: Docling + сборка/запуск Java/Grobid | Один Docling; Grobid в основной проход не включён |
| Книги: разбиение по закладкам, без них весь PDF | Физические PDF-части максимум по 10 страниц независимо от закладок |
| Деление после отдельных ошибок памяти | Распознавание CUDA OOM, MemoryError, bad_alloc; рекурсия до 1 страницы |
| Итоговый файл после обработки книги | Checkpoint после каждой успешной части, на Drive по умолчанию |
| Повторная загрузка очищает рабочие каталоги | Каталоги не очищаются; продолжение по SHA-256 файлов |
| Самописный рендер каждого элемента | Штатный Markdown-сериализатор Docling для каждой страницы |
| Плейсхолдеры изображений и общая нумерация | PNG и ссылки с уникальными именами по диапазону/номеру картинки |
| Ошибка части могла остаться лишь комментарием | Статус `incomplete`, явный список пропущенных страниц и ошибок |
| Автоматическое исправление похожей на CP1251 кириллицы | Нет автоматической замены символов в медицинском тексте |

Из книжного варианта сохранены идея абсолютных номеров страниц и деление при
нехватке памяти. Ноутбук статей использован для сопоставления этапов; его
Java/Grobid-сервис, извлечение метаданных статьи и разметка контекстов цитирования
не перенесены. В этом варианте **нет структурированного `references.json`**:
список литературы, номера ссылок, комментарии к рекомендациям и приложения
остаются в тексте. Отдельное извлечение библиографии можно делать после проверки
полноты конвертации; оно не должно блокировать основной проход.

OCR: EasyOCR, русский + английский, GPU; по умолчанию распознаются подходящие
области без принудительного OCR всей страницы. `FORCE_FULL_PAGE_OCR=True` —
отдельный вариант для плохого текстового слоя. Таблицы: ACCURATE с сопоставлением
ячеек; сохраняется также HTML. Отдельная модель формул выключена для экономии
памяти: включается `FORMULAS=True`. Схемы сохраняются как картинки; понимание
стрелок и логики алгоритмов не заявлено.

Используется публичный API `PdfFormatOption/PdfPipelineOptions`, без прямого
выбора внутренних backend/pipeline-классов. Batch sizes = 1, очередь = 2,
масштаб изображений = 1.5; изображения целых страниц не сохраняются.
Штатный экспорт и сохранение изображений сверены с
[документацией Docling](https://docling-project.github.io/docling/reference/docling_document/)
и [официальным примером](https://github.com/docling-project/docling/blob/v2.103.0/docs/examples/export_figures.py).

## Особенности предоставленных PDF

Локально проверена структура файлов, без полного запуска моделей:

| Файл в `docs/clinrecs/` | Страниц | Верхних закладок | Страницы с <80 символами текстового слоя |
|---|---:|---:|---|
| `0540e25c52977eca81007182ae8146fd.pdf` (депрессия) | 125 | 19 | 1, 101, 102 |
| `1e242790a59b9e5c571386bea45fe13a.pdf` (ГТР) | 121 | 0 | 1, 87 |

Для каждого полного PDF получается 13 первоначальных частей. Последние части —
5 и 1 страница соответственно. Деление при OOM может увеличить число частей.
Мало текста не означает пустую страницу: титулы, таблицы и схемы требуют OCR
или проверки сохранённого изображения. Номера здесь и в результатах — страницы
PDF с 1; напечатанная в документе нумерация может отличаться.

## Выходные файлы и продолжение

Каждому PDF/настройкам/версии кода/основным версиям библиотек соответствует
отдельная папка `<имя PDF>_<fingerprint>/`. После пробного диапазона полный
документ будет обработан в отдельной папке; пробные части автоматически туда
не переносятся. Вернуться к прежним настройкам — продолжить прежний запуск.

- `document.md` — выбранный диапазон в порядке PDF, маркеры `<!-- page: N -->`,
  реальные ссылки на изображения. Для неудачных страниц стоят явные заглушки.
- `pages.jsonl` — Markdown, абсолютная и локальная страница, часть, предупреждения.
- `images/` — отдельные PNG.
- `chunks/pNNNN_NNNN/docling.json` — исходный DoclingDocument для части;
  локальные страницы/ID/координаты, встроенные изображения. Между частями JSON
  не конкатенируются: ID и локальные номера там могут совпадать. Привязка к
  исходному PDF задаётся диапазоном части и `local_page`/`pdf_page` в pages.jsonl.
- `chunks/.../table_NNNN.html`, `tables.json` — HTML таблиц и их привязка к PDF.
- `manifest.json` — SHA-256 исходного PDF и скрипта, настройки, версии, свойства PDF.
- `outline.json` — закладки PDF, если есть. Это не распознанное текстовое оглавление.
- `quality_report.json`, `REPORT.md` — результат и места для проверки.
- `chunks/.../checkpoint.json` — данные успешной части и SHA-256 её артефактов.
- `chunks/.../split.json` — сохранённое решение разделить часть после OOM.

Проверяется наличие и SHA-256 каждого файла, на который ссылается checkpoint.
Повреждённая часть будет обработана повторно; неудачные части тоже повторяются.
Частичный успех Docling не считается успешным checkpoint. Необработанные
страницы не скрываются при слиянии. Отчёт обновляется после каждой исходной
части, checkpoints — после каждой успешной половинки.
При обрыве kernel/питания последний отчёт может отставать от checkpoints;
повторный запуск восстановит его. После обычного KeyboardInterrupt отчёт
пересобирается в `finally`.

Если Colab жёстко завершает среду на одной и той же части, Python не может
перехватить такую ошибку. Уменьшите `CHUNK_PAGES` до 5 или 2; это создаст новый
запуск. При ошибке даже одной страницы она останется в списке пропусков.

`complete` означает покрытие всего PDF без исключений конвертации,
`preview_complete` — покрытие только выбранного диапазона, `incomplete` — пропуски.
Ни один статус не подтверждает качество OCR. Автоматические предупреждения:
мало Markdown, заметное уменьшение объёма относительно текстового слоя,
оставшийся плейсхолдер изображения, изображения без пикселей и многостраничные
таблицы. Это эвристики; все границы частей также перечислены для просмотра.

Таблицы/абзацы через границы страниц и частей **автоматически не объединяются**.
Оглавление, колонтитулы и примечания не удаляются. Нумерация и уровни заголовков
определяются Docling и могут требовать правки. Дозировки, ссылки, знаки ≥/≤,
рекомендации с УУР/УДД и шкалы нужно сверить с источником перед использованием
для RAG. Этот этап — конвертация, а не подготовка утверждённого клинического корпуса.

## Файлы для разработки и локальная проверка

`clinrecs_pipeline.py` — тот же код отдельно для CLI/редактирования.
`build_notebook.py` обновляет встроенную копию скрипта в ноутбуке:

```bash
python3 scripts/clinrecs/colab/build_notebook.py
python3 -m unittest discover -s scripts/clinrecs/colab -p 'test_*.py'
```

Девять тестов используют настоящие pypdf и сериализатор docling-core,
синтетические документы и подменённую конвертацию: порядок/полнота,
изображения/таблицы/примечания/номера страниц, восстановление после обрыва,
проверка повреждённых артефактов, OOM и деление до одной страницы,
повтор только неудачных частей, частичный успех и изоляция запусков.
Сеть и модели в тестах не используются.

Для CLI на подготовленной GPU-машине:

```bash
python3 scripts/clinrecs/colab/clinrecs_pipeline.py \
  docs/clinrecs/0540e25c52977eca81007182ae8146fd.pdf \
  docs/clinrecs/1e242790a59b9e5c571386bea45fe13a.pdf \
  --output /tmp/parsed_clinrecs --chunk-pages 10
```

CLI возвращает код 1 при ошибках/пропусках. Для осознанного медленного CPU-прогона
есть `--device cpu`; здесь полный прогон не выполнялся.

В ноутбуке закреплены Docling 2.103.0, docling-core 2.82.0, EasyOCR 1.7.2,
pypdf 6.13.3. Штатные torch/torchvision Colab используются как установлены;
полный транзитивный lock не заявлен. Основные фактические версии записываются
в manifest; по `pip freeze` из удачного Colab-прогона можно закрепить всё окружение.
Новые библиотеки используются только в автономном Colab-инструменте:
Docling/core — MIT, EasyOCR — Apache-2.0, pypdf — BSD-3-Clause.
Ревизии и лицензии автоматически загружаемых весов отдельно не аудированы;
сборка для эксплуатации и интеграция в приложение в эту задачу не входят.

Проверены схема ноутбука, синтаксис ячеек, совпадение встроенного скрипта,
настройки публичного API Docling и девять офлайн-тестов.
**Полный OCR этих PDF и запуск на Colab GPU ещё не проверены.** Исходные PDF,
исходные два ноутбука, приложение и база не изменялись.
